# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

ModernC23 is a small C11/C++ CMake project: a `lib` static library, an `app` executable that consumes it, and a GoogleTest suite. It exists as a scaffold/learning project, so keep additions minimal and consistent with the existing structure rather than introducing new layers.

## Build system

- Requires CMake **4.2+**.
- Windows-only presets today (`CMakePresets.json`), targeting Visual Studio 18 2026 (toolset `host=x64,version=14.51`), in 32-bit and 64-bit / Debug and Release combinations:
  - `windows-x86-32-debug`, `windows-x86-32-release`, `windows-x86-64-debug`, `windows-x86-64-release`
  - `windows-x86-64-clang` builds the same 64-bit sources with clang-cl (Ninja generator) instead of MSVC/cl.exe; it's a single Debug-only preset, not a debug/release pair.
- Dependencies are managed via **vcpkg in manifest-less mode, driven by the root `CMakeLists.txt`**, not a `vcpkg.json`:
  - If `VCPKG_ROOT` env var is unset, it clones vcpkg into `.vcpkg/` and bootstraps it automatically on every configure.
  - If `VCPKG_ROOT` is set, that existing checkout is used instead (faster, avoids the auto-clone/pull).
  - The per-arch toolchain files under `cmake/windows-x86-32/toolchain.cmake` and `cmake/windows-x86-64/toolchain.cmake` set `CMAKE_SYSTEM_*` and include vcpkg's `vcpkg.cmake` toolchain. `cmake/windows-x86-64-clang/toolchain.cmake` does the same but also locates clang-cl.exe via `vswhere` (since VS's `VC/Tools/Llvm` may live on any drive) and points `CMAKE_C_COMPILER`/`CMAKE_CXX_COMPILER` at it.
  - Currently the only vcpkg dependency is `GTest`.

### Common commands

```sh
# Configure
cmake --preset windows-x86-64-debug

# Build
cmake --build --preset windows-x86-64-debug

# Run the full test suite (via ctest)
ctest --preset windows-x86-64-debug
```

Swap `windows-x86-64-debug` for any of the other three preset names as needed.

### Running a single test

The GTest suite is registered with ctest as one executable (`ModernCTest`), so `ctest` alone always runs the whole binary. To run/filter individual cases, invoke the built test executable directly with GTest's own filter flag, e.g.:

```sh
_build/windows-x86-64-debug/tests/Debug/ModernCTest.exe --gtest_filter=Lib.returns_expected_value
```

(Path is under the preset's `binaryDir`, `_build/<presetName>/`, with a per-configuration subfolder since the VS generator is multi-config.)

Note: a `cmake-build-debug/` directory is also present, generated by CLion using Ninja + the local VS toolset directly (bypassing `CMakePresets.json`). Prefer the documented presets above unless the user specifically asks about CLion's own build.

## Architecture

- `src/` — the `lib` target (static library). Source in `src/lib/lib.c`, public header in `src/lib/include/lib.h` (exposed via `target_include_directories(... PUBLIC)`). New library code belongs here; keep the public API surface in `src/lib/include`.
- `app/` — the `app` target (executable), links against `lib` and demonstrates its API in `main.c`.
- `tests/` — the `ModernCTest` target (C++/GTest). `RunAllTests.cpp` is the GTest main; all other `*.cpp`/`*.h` in this directory are glob-included automatically by `tests/CMakeLists.txt`, so a new test file just needs to be added here (no CMake edit needed). Tests link against `lib` and include `../src` for headers, and call into `lib.h`'s C API via `extern "C"`.
- Root `CMakeLists.txt` enforces C11 for C targets, enables testing, and adds subdirectories in order: `src`, `app`, `tests`.
